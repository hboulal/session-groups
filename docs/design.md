# Session groups — design

## Intent

A VS Code extension that lists your coding-agent sessions in groups you define yourself, runs each session in a real VS Code terminal, and brings every session back after VS Code is closed and reopened: the group and its sessions are still listed, and clicking a session resumes it.

Why: the official Claude Code extension does not offer the terminal, groups its sessions by folder rather than by groups you choose, and lists the sessions it loads from Claude itself, whereas this extension lists exactly the sessions you opened from it.

## Goals

- A side panel with your groups, each listing the sessions started from it.
- A group is yours: a name, a colour, the folder its sessions start in, and the shell its terminals use.
- "+" on a group starts a new session in a new terminal.
- Sessions persist across VS Code restarts; clicking one resumes it in a terminal.
- Several agents: an agent is a profile (a name and two command templates); Claude, OpenCode, Copilot, Gemini, Qwen Code and Goose are built in, more are configured, and one group can mix sessions of different agents.
- Rename and delete for groups and sessions from the panel.

## Non-goals (v1)

- Listing sessions started outside the extension (plain terminal, official extension); one is added only by its id (see "Add Existing Session"). The only agent file the extension reads is a session's own Claude transcript, for its title (see "Rename / delete") and, when an existing session is added, its folder.
- Keeping sessions running after VS Code closes (Claude's `--bg` / `attach` background sessions are a possible later step).
- Syncing groups or sessions between computers.
- An agent that cannot start a session with an id chosen beforehand (Codex today: `codex resume <id>` exists, a start-with-id option does not).
- Awareness across VS Code windows: clicking a session that runs in another window starts a second resume there. Added only if it starts to hurt.

## Anti-goals

- A session started from the extension that is missing from the list after a restart.
- A webview chat UI: the session is the agent's own terminal UI, untouched.
- Deleting anything the agent owns: delete removes the list entry only, never the agent's transcript.

## Behaviour

**Create a group.** The panel has two views, "Groups" on top and "Archived" below it, each of which can be collapsed or resized. The Add Group button (new-folder icon) in the Groups view's title bar adds a group: name, folder (a folder picker opening at the `sessionGroups.defaultFolder` setting), shell (defaults to the VS Code default terminal profile); the colour is the next one of the list (see "Colours").

**Group settings.** A group row has two inline buttons, "+" and a gear "Group Settings" that opens a menu (Rename, Change Color, Change Folder, Change Agent, Delete Group, Delete Group and Sessions); its right-click menu has New Session With… and the same two deletes. The settings menu has the title `Group: <name>`, no placeholder, and a separator before the two deletes. It shows the current values; only the picked one is asked for. A new folder applies to new sessions only.

**Default folder.** The setting `sessionGroups.defaultFolder` is where an ungrouped session starts and where the folder picker opens; empty means the first workspace folder, else the home folder.

**New session.** The extension generates the session id (a UUID, or in the agent's own format, see "Agents"), opens a terminal in the group's folder and shell, without a name so its tab shows the title Claude sets (as in a terminal opened by hand), then sends the agent's start template with the id filled in, e.g. `claude --session-id <uuid>`. "+" on a group starts the group's agent; "New Session With…" (right-click menu of a group or of the Ungrouped row) asks which agent. "+" is the only icon that starts a session. It stores the session: id, group id, the folder it started in, shell, agent, display name, created date. A new session's display name is its local start date and time (`YYYY-MM-DD HH:mm`) until Claude names it (`/rename`) or it is renamed in the panel.

**Ungrouped session.** The "+" on the Ungrouped row starts a session that belongs to no group (`groupId` empty): the VS Code default shell, the default folder (see "Default folder") as working directory, the start date as display name. Ungrouped sessions are listed under an expanded "Ungrouped" row in the Groups view, below the groups, with their count as description, the "+" button on its row and "New Session With…" in its right-click menu, in your order (see "Order and drag and drop"), and resume, rename and delete like any other. The Ungrouped row is listed whenever a group or a non-archived ungrouped session exists, regardless of the active filter; with neither, the grouped root is empty and shows the welcome contents.

**Session age.** Each session shows how long ago it was first started: `today`, `1 day`, `N days` (whole local calendar days between its created date and today).

**Group count.** Each group and Ungrouped show the total number of their non-archived sessions, followed by the active count when positive (`5 · 2 active`, otherwise `5`), regardless of the active filter. Archived-view group rows show only their archived count.

**From the Explorer.** Right-clicking a folder in the Explorer shows two entries (a single folder only, hidden from the Command Palette). "New Grouped Session Here" starts a session in the group whose start folder is that folder, asking which one when several are; when none is, it first asks for a group name, prefilled with the folder's name, and adds a group starting there with the default shell and the next colour. "New Ungrouped Session Here" starts an ungrouped session in that folder. A group without a start folder whose "before" command is a lone `cd <path>` counts as starting in that path. A start folder matches exactly, ignoring a trailing slash, and on Windows also case and the kind of slash. Group names and start folders need not be unique.

**Add Existing Session.** Right-click a group or Ungrouped → Add Existing Session… lists a session started elsewhere: its id (checked like Edit Session ID) for the group's agent, the date it was added as name (the Claude title replaces it once its terminal is open), the group's shell. A Claude session's folder is the last `cwd` its transcript records, else the group's folder, the default folder, the workspace, home. It is not opened; a click resumes it.

**Edit Session ID.** Right-click a session (in either view) → Edit Session ID points the entry at another session of the same agent, keeping its group, place and name; the new session's `/rename` title is picked up again. The id must match the agent's `idPattern` (Claude: a UUID; OpenCode: starts with `ses`; an agent without one: any id without spaces) and must not already be listed, since VS Code needs one row per id and two entries would resume the same session twice. Whether the session exists is left to the agent, which reports it in the terminal. Refused while the session's terminal is open.

**Session buttons.** A session row in the Groups view has two inline buttons, Rename and Archive, including while its terminal is open. Its right-click menu groups Open Session and, only with an open terminal, Close Terminal under `0_open`; Rename Session, Archive Session and, only without an open terminal, Edit Session ID under `1_modify`; Delete Session under `9_delete`. Close Terminal closes the terminal and keeps the session entry. A row in the Archived view has Unarchive as its inline button, and Rename, Edit Session ID and Delete in its right-click menu.

**Archive.** Archiving hides a session from its group (or from the ungrouped list) and lists it in the Archived view, in stored order, with the count as the view's description (hidden at 0); the active filter does not affect that view. Archived rows show an archive icon (the green terminal icon while their terminal is still open), their group name and their age, with the agent name first when it is not Claude. Archiving is the extension's own: it never touches the agent's transcript. An archived session cannot be opened (its row takes no click and says "Unarchive to open", search leaves it out); archiving a session whose terminal is open asks whether to close the terminal (Archive and Close, Archive Only, or cancel). A trash button ("Clear Archived") in the Archived view's title bar removes every archived session from the list after a confirmation, closing any terminal still open; the transcripts are kept; when nothing is archived it says "Nothing is archived.". A button in the Archived view title toggles between that list and the archived sessions under their groups (only groups with an archived session, then Ungrouped, each with its count; the rows then show only their age); the choice is remembered across restarts. Unarchive puts it back where it was. A stored session without an archived flag is not archived.

**Search.** A search button in the Groups view title opens a quick pick with the placeholder "Search sessions", listing sessions that can be opened under group-name separators in tree order, then Ungrouped, with sessions in their stored order and empty sections omitted. Archived sessions are left out. Each session shows its age, preceded by its agent name except for Claude (an unknown agent shows its id); running sessions use the green active image icon, others the history icon. Typing filters session names and descriptions, not group names; picking one resumes or focuses it like a click.

**Look.** The extension icon is a 16×16 pixel-art drawing of three stacked terminal windows (purple, blue, and a green front one with a `>_` prompt), `media/icon.png` at 128 px; the activity-bar icon is the same drawing in one colour, `media/activity.svg` (VS Code tints it), Add Group uses `new-folder`, and session-start row buttons use `add`. In the Groups view, with or without group rows, a grouped session's icon carries its group's colour as a small square in its bottom-right corner while group colours are shown (images shipped in `media/marked/`, drawn by `src/icons.ts` and kept equal to it by a test, in the default dark and light chart colours; the working spinner cannot carry it; ungrouped sessions and the Archived view keep plain icons). A session tooltip shows, each on its own line, its bold name (`unnamed` when empty), agent name (id if unknown) and state (`running` for an open terminal, `not running`, or `archived` in Archived), `Created YYYY-MM-DD HH:mm` and, for Claude, `Last active` (its transcript's modification time, read when the tooltip opens), its folder only when it is not the one its group starts in (for Ungrouped: the default folder), the "before" command when set, and its id; archived tooltips end with "Unarchive to open". A group's tooltip (and Ungrouped's) shows its name, the folder its sessions start in (marked "default folder" when it comes from the setting), its agent (marked "default agent" when the group has none chosen) and its session and running counts. User text is escaped as text within the Markdown tooltip. Empty grouped Groups shows "No sessions yet. Start one in a folder, or [add a group](command:sessionGroups.addGroup) to keep related sessions together." and a New Session button on its own line; empty flat Groups shows "No sessions to show." or, with the active filter, "No session is running."; empty Archived shows "Archived sessions appear here." The Command Palette exposes only Add Group, Search Sessions, New Session With… and New Session (ungrouped); view toggles and row actions are hidden.

**Keys.** While the Groups or Archived view has focus (and no input box), F2 renames the selected session or group. Delete (Cmd+Backspace on macOS) in Groups archives the selected session (asking about its open terminal as Archive does) or deletes the selected group as Delete Group; in Archived it deletes the selected session after a confirmation. A mouse middle-click cannot be used: the tree view API reports no mouse events.

**Order and drag and drop.** Rows can be dragged whenever groups are shown; without groups they cannot, since a drop would still move sessions between the hidden groups. Groups and sessions are shown in the order you give them, stored as their order in the saved lists; a new group goes last, a new session goes first in its list. Dragging a group onto another group puts it before that group; onto a session in a group, before that session's group; onto an ungrouped session, the Ungrouped row or empty space, last. Dragging a session onto another session puts it before that one, in that session's group (or among the ungrouped); onto a group moves it to the end of that group, since reordering across lists needs it; onto the Ungrouped row or empty space makes it ungrouped, last. Moving a session to another group changes only where it is listed: it keeps its own "before" command and folder. Drag and drop happens in the Groups view only, so archived sessions cannot be dragged; the Ungrouped row cannot be dragged.

**Without groups.** A button in the Groups view title, "Show Sessions Without Groups" (list icon; "Show Groups", tree icon, goes back), lists the non-archived sessions without group rows (archived ones are in the Archived view), each with its icon marked by its group's colour (see Look), or labelled `<group>/<session>` while group colours are hidden (an ungrouped session keeps its name), in group order then the ungrouped ones; the active filter works as in the grouped view. The choice is remembered across restarts. Starting a session in a group needs the grouped view.

**Colours.** Each group row has a coloured dot, so groups stand apart from their sessions; a new group takes the next colour of a fixed list (blue, purple, orange, yellow, red; green is kept for active sessions), and Change Color in the group's menu picks another. "Hide Group Colors" in the Groups view title's "…" menu removes the dots (and the Ungrouped outline) in both views, "Show Group Colors" brings them back; the choice is remembered across restarts and does not touch the green active icon.

**Active filter.** A session is active when its terminal is open in this window. Active sessions have a distinct icon, in green, rendered as an image in `media/` with light and dark variants; its colour on a selected row is to verify by reload. A toggle in the Groups view title (a lightning icon; while on, a "Show All Sessions" icon) shows only active sessions (groups stay visible so "+" is still reachable; the Archived view is not affected) and back to all. Group and Ungrouped counts show both the non-archived total and a positive active count in either filter state. The number of active sessions is always visible: next to the Groups view title (`N active`, hidden at 0) and as a badge on the activity-bar icon.

**Follow the terminal.** When a session's terminal becomes the active terminal (picked in the terminal panel or its tabs) and the Groups view is visible, the session's row is selected, without taking the focus from the terminal; archived sessions and a hidden panel are left alone, since revealing a row opens its view.

**Turn status (Claude, OpenCode).** While a Claude session's terminal is open, the poll that reads its `/rename` title also reads whose turn it is from the same transcript tail: the last non-sidechain, non-meta `user` or `assistant` entry decides; an assistant entry with `stop_reason` `end_turn`, a user entry carrying "[Request interrupted", or a compaction summary (a user entry with `isCompactSummary`), means Claude is done (your turn), anything else means working (verified on real transcripts). A working session shows a spinning `loading~spin` icon; a done one the green terminal image. When a session goes from working to done while its terminal is not the active terminal of a focused window, it is marked unseen (the green terminal with a yellow dot, an image like the active icon so selection keeps its colours) and a notification "<name> finished." offers Open; the mark clears once its terminal is in front in a focused window, or when the terminal closes. The setting `sessionGroups.notifyWhenFinished` (default on) turns the notification off. Turns are kept in memory only, so after a reload the first reading sets the state without a notification. A Claude session waiting on a permission prompt looks like working, since the transcript does not record the prompt. OpenCode sessions get the same states from OpenCode's database (`$XDG_DATA_HOME/opencode/opencode.db`, else `~/.local/share/opencode/opencode.db`), read-only through `node:sqlite` (present in the extension host's Node 24; without it the state is simply not shown): the session's last `user`, `assistant` or `idle` row in `session_message`, by `seq`, decides, `idle` meaning done (verified on a real database). Copilot, Gemini, Qwen Code and Goose show the plain running icon: their session records were not available to check. The tooltip state reads `working`, `running, your turn`, `finished, not seen yet`, `running` (no reading yet) or `not running`.

**Resume.** Clicking a session whose terminal is still open in this window focuses that terminal. Otherwise it opens a new terminal in the session's stored folder and sends the resume template: `claude --resume <uuid>`. The stored folder is used, not the group's current one, so editing a group never moves its old sessions.

**Rename / delete.** Renaming a group or session changes its display name in the panel only; the terminal tab keeps Claude's title. Renaming inside Claude (`/rename`) renames the session: while a session's terminal is open, the extension reads the end of its transcript (`<claude config dir>/projects/*/<id>.jsonl`, config dir `CLAUDE_CONFIG_DIR` or `~/.claude`) every few seconds, and when the last `custom-title` entry differs from the last Claude title it applied, it sets the session's name to it. A rename in the panel therefore holds until the next `/rename` in Claude. Deleting a session removes it from the list (and closes its terminal if open). Delete Group removes only the group immediately, without confirmation, and all its sessions, archived ones included, move to Ungrouped with their terminals left open; Delete Group and Sessions asks for confirmation, then removes the group and every session entry in it, archived ones included, closing their open terminals (the agents' transcripts are kept).

**Agents.** An agent is `{ id, name, start, resume, idPrefix?, idPattern? }`; `{id}` in the templates is the session id. Built in: Claude (`claude --session-id {id}` / `claude --resume {id}`) and OpenCode (`opencode --session {id}` for both, `idPrefix` `ses_`: OpenCode rejects an id not starting with `ses`, and creates the session when the id is new, both checked with `opencode run`); Copilot, Gemini and Qwen Code (`<cli> --session-id {id}` / `<cli> --resume {id}`, `idPattern` a UUID; the flags checked in `--help` of copilot 1.0.105, gemini 0.67.0 and qwen 0.26.7); Goose (`goose session -n {id}` / `goose session --resume -n {id}`: Goose assigns its own ids, so the extension's id is used as the session name; from the Goose documentation). Codex, Cursor, Kiro, Crush and Amp are left out: none can start a session with an id given to it. The setting `sessionGroups.agents` adds agents or replaces a built-in one by id; an entry missing a field or `{id}` is skipped with an error message. `sessionGroups.defaultAgent` (default `claude`) is the agent of sessions without a group and of groups with none chosen; Change Agent in the group's menu sets its own. A session keeps the agent it started with and always resumes with it. A session row names its agent before its age, except for Claude. Reading the `/rename` title is Claude-only.

## Decisions

- Storage is the extension's own VS Code storage (global state), on this computer only. Rationale: sessions cannot resume on another computer anyway, since agent transcripts stay local.
- The extension chooses the session id before launch (`claude --session-id`, verified in `claude --help`), so it never has to discover an id afterwards.
- Groups and sessions stored with a "before" command (a free-text command run in the shell before the agent) keep it: their sessions replay it, and a group's one is dropped when Change Folder sets a folder. The extension does not offer setting it; a folder replaces the `cd`.
- Every session stores the working directory its terminal opened in (resolved at creation), and resume opens the terminal there, so a session resumes where it started, whichever window is used.
- The shell is stored resolved, as a shell path without arguments (prefilled from VS Code's default shell), at group creation; changing VS Code's default profile later does not change existing groups.
- Session terminals survive a window reload: they are ordinary terminals, and the extension remembers each open session terminal's process id per window, so after a reload it re-attaches to the terminal VS Code reconnects (same process id) and the running session goes on. The extension also keeps each terminal's latest title. After a full VS Code restart, VS Code revives a terminal under that title but with a new, empty shell; the extension closes it, so a click resumes in a fresh terminal.
- A session entry is written when its terminal opens and kept even if the launch fails; a failed resume shows its error in the terminal and you delete the entry. No launch-outcome detection in v1.
- Local windows only in v1: remote windows (WSL, SSH, dev containers) are a non-goal.
- Writes to storage re-read the current list and change one entry, never write back a stale copy, one at a time within a window. Across two windows this is not guaranteed (each window's storage view may be stale), so two windows adding sessions at once can lose one; accepted with the non-goal on cross-window awareness.

## To verify

- By reload: menus on running sessions, welcome views, quick-pick separators with image icons, and the green active SVG on a selected row.
- That interactive `opencode --session <id>` behaves as `opencode run --session` does.
- That Copilot, Gemini and Qwen Code create a new session for an unknown UUID given to `--session-id`, and resume it with `--resume`.
- That Goose starts and resumes by name as documented (not checked against an installed Goose).
- That a reconnected terminal after a reload reports the same `processId`, and a revived one after a restart keeps its last title; that an unnamed terminal's `name` follows the title Claude sets. Not checked in a real VS Code yet.
- `sendText` timing before the shell is ready: no failure has been reported, but this case was not tested on purpose; watch for a lost first command with slow shells.
